# 08 — ChatGPT-First 專案初始化簡報

> 這份文件是給**下一個專案**的起點，不是這個專案的一部分。
>
> 它把 P1 Driving English Coach 從零做到上線、並在真實通勤中使用之後累積的
> 需求、決策與實測數據整理出來，讓平台換成 ChatGPT 之後不必重新踩一遍。
>
> 每一條決策後面都附了理由。理由比結論重要 —— 換了平台之後，有些結論會失效，
> 但讓它成立的那個理由通常還在。

---

## 1. 產品是什麼

把通勤時間變成英文口說練習。一天一次，三段式：

| 階段 | 情境 | 設計要求 |
| --- | --- | --- |
| **出發前** | 車停著，可以看螢幕、可以打字 | 30 秒完成設定 |
| **行進間** | 開車中，不能看、不能打字 | 只用聲音；螢幕只有狀態與大按鈕 |
| **抵達後** | 車停好，可以慢慢看 | 一份看得完的回顧 |

這個三段式邊界是整個產品的骨架。**任何新平台方案都要能撐住這三段，尤其是中間那段。**

---

## 2. 平台變更：ChatGPT 為主體

### 動機

API 計費的實測成本是 **每分鐘約 $0.024**。以每週 5 天、每次 1 小時計，約 **$31/月**。
ChatGPT Plus 是 $20/月固定價，且免費帳號的文字對話已無上限。把對話本身移到
ChatGPT，等於把最大一筆變動成本換成固定成本。

### 硬限制（先看這個再規劃）

**ChatGPT 的 Voice Mode 目前不支援 Apps SDK 的 app / widget。**

這一條決定了架構。它的意思是：

- 用 **Apps SDK** 做出來的 app 可以有自己的 UI、可以存資料，但**開車時用不到**，
  因為它進不了語音模式。
- 用 **Custom GPT / Project 指令**承載教練人格，可以在 Voice Mode 裡跑，
  開車時可用，但**沒有 UI、拿不到結構化資料**。

也就是說「開車時的語音」和「app 的介面與資料」目前**接不起來**，這不是設計問題，
是平台能力還沒到。規劃時必須假設它短期內不會改變；如果改變了，架構可以收斂，
但不能一開始就賭它。

### 第二個硬限制：拿不到逐字稿

第三方 app 讀不到 ChatGPT 對話的內容。而這個產品「抵達後」那一段的**全部價值**
都建立在逐字稿上 —— 回顧、修正、字詞、儀表板統計，沒有一個能憑空產生。

**這是整個轉向最關鍵的未解問題。** 見第 9 節。

## 3. 三個可行方案

### 方案 A — 全部留在 ChatGPT 內

Custom GPT（或 Project）承載教練指令，開車時用 Voice Mode，抵達後在同一個對話裡
叫它產生回顧，用 ChatGPT 的 Memory 記住進度。

- 成本：$0（或 Plus $20/月）
- 開發量：極小，就是寫指令
- 代價：沒有儀表板、沒有可靠的間隔複習排程、沒有跨次數的統計、資料在 ChatGPT 裡
  拿不出來也備份不了。Memory 不是資料庫，它會忘、會混淆、無法查詢。

**適合**：只要「有人陪我練」，不要「看得到進步」。

### 方案 B — ChatGPT 負責講，自建 app 負責記（推薦）

- **行進間**：ChatGPT Voice Mode + Custom GPT。零 API 成本。
- **出發前／抵達後**：自建的輕量 app（web 或 Apps SDK），負責主題管理、回顧、
  儀表板、間隔複習。
- **橋接**：抵達後在 ChatGPT 裡下一句固定指令，讓它輸出**約定格式的 JSON 或表格**，
  複製貼上到 app 裡。app 解析後入庫。

- 成本：對話 $0；回顧解析可以用便宜文字模型（約 $0.002/次）或直接由 ChatGPT 產生
  好格式、app 只做解析（$0）
- 開發量：中等，但**現有專案的資料層、回顧格式、儀表板、間隔複習可以幾乎原封搬過去**
- 代價：多一個「複製貼上」的動作。這是目前唯一能把資料弄出 ChatGPT 的路。

**適合**：想保留「看得到進步」，也想把成本壓到接近零。**這是我的建議。**

### 方案 C — 維持現狀（API 自建）

- 成本 $31/月，但體驗完整、資料自有、開車時的 UI 是為開車設計的。

**適合**：如果每月 $31 換 20 小時口說練習你覺得划算（一小時真人家教約 $20–40），
其實不需要換。

## 5. 硬性限制（不可妥協）

這些是原始需求就定下的，換平台不改變：

- **不假設鎖定畫面上的完整操作**
- **不依賴語音喚醒字**
- **不做 CarPlay / Android Auto 深度整合**
- **行進間不能要求使用者看螢幕、讀文字、打字**
- **手機優先**；桌機只要能開就好
- **公開可部署、可展示**（作品集用途）
- **不過度工程，不預先建造用不到的東西**

新增一條，由這次的實測得出：

- **不做發音教學。** 見第 6 節。

## 6. 已經付出代價換來的決策

這一節是這份文件最值錢的部分。每一條都是實際做出來、實際用壞、才改掉的。

### 6.1 教練要「操練」，不要「聊天」

模型放著不管會變成溫暖、什麼都同意的聊天對象：不斷稱讚、每輪換話題、從不重複。
感覺很好，教不到東西，而且**稱讚佔掉的是使用者開口的時間**。

指令必須明確要求：
- 一次只練**一個句型**，換四五個情境重複，練到自動
- **點名禁止**稱讚詞（great job / well done / nice / excellent / that's a great point）
- 不評論內容，只評論英文
- 不做總結、不預告
- 每輪一到兩句；「你的回合比學生上一輪長就是太長了」
- 學生正確用過約四次後**直接問**要不要換句型

### 6.2 糾正要慢、要分開、要對比

使用者看不到字，**聽出差別是唯一的管道**，而正常語速下一個字的差異聽不出來。

四步流程，所有等級一律放慢：
1. 慢慢說出他講的：「You said: I have went there.」
2. 只點出錯的那塊：「The problem is 'have went'.」
3. 慢慢說正確版，**重音在改掉的字**：「It should be: I have GONE there.」
4. 讓他跟著說一次

錯的和對的中間要有明顯停頓。

### 6.3 不做發音教學

實測發現教練會糾正**其實唸對的字** —— 車上開擴音、有路噪，聽起來不對的多半是收音
問題。而且文字逐字稿分不出「唸錯」和「辨識錯」。

**被告知你唸錯了一個其實唸對的字，比完全沒有回饋更糟**，因為它會賠掉使用者對其他
所有回饋的信任。

界線：**只有在教練真的聽不懂、請對方重講、還是聽不懂**時才處理。那判斷的是
「溝通有沒有成立」這個事實，不是口音好壞。口音不是錯誤，只有聽不懂才是。

### 6.4 不產生分數

用一份不完美的逐字稿生出 0–100 的數字是假精確，而且一旦顯示出來使用者就會當成量測
結果。改成統計**真實發生過的事**：重複出現的錯誤類型、開口分鐘數、練習頻率。

### 6.5 統計要算「實際發生」而不是「當初選的」

原本把使用者在設定頁挑的時長加總，結果是：進設定頁選一選然後關掉五次，畫面顯示
「已練習 75 分」。改成用開始／結束時間實算，沒完成的算 0 並標「未完成」。

**通則：任何顯示給使用者的數字，都要問一次「這是意圖還是事實」。**

### 6.6 趨勢看規律，不看表現

每週開口分鐘數的長條圖，**空白的那幾週也要畫出來**。這個產品成不成立取決於有沒有
持續用，空白才是重點。

### 6.7 間隔複習用三段就好

1 天、7 天、30 天。三段是遺忘曲線真正轉折的地方，也是**人腦記得住的排程** ——
記不住的排程等於不會信任的排程。更多段還會讓一個片語要點更多次才能清掉，而
這面牆的目的是**清空**。

同一個片語重複出現時，保留**複習進度最多**的那一筆，否則新的那筆會把進度歸零，
甚至讓已經走完消失的片語復活。

### 6.8 回顧「第一次打開時」才產生

不要在練習結束時產生 —— 那時使用者正要把手機收起來，不該卡在轉圈圈上；而且沒人
看的回顧不該花錢。同一次練習只產生一次。

### 6.9 壞掉的功能不要顯示

一個永遠收不到驗證碼的輸入框，比「沒有這個功能」更糟：前者看起來像產品壞了，
後者只是還沒做。**依賴外部設定的功能要放在旗標後面，設定沒到位就不出現。**

## 7. 實測數據

| 項目 | 數值 |
| --- | --- |
| 成本（優化後） | **$0.024/分鐘** |
| 47 分鐘一次練習 | **約 $1.12** |
| 成本結構 | audio output **68%**、audio input 13%、cached 8%、text 10%、transcribe 1% |
| 每週 5 天 × 1 小時 | 約 **$31/月** |

**關鍵發現**：成本的大宗是**教練在講話**（output 按時長計費），不是使用者在講話。
所以「讓教練少講」同時是教學改善和成本改善。A2 這種要求「講慢」的等級，成本天然
較高，這是教學需要，不是可以優化掉的。

第二個發現：對話歷史會**每一輪重新計費**。加上截斷設定後，input 從 $0.57 降到
$0.06（15 分鐘），且成本從隨長度加速累積變成**與時間成正比**。

> 這兩點在 ChatGPT 方案下都不再是成本問題，但**「教練話太多」仍然是教學問題**。

## 8. 真實環境中壞掉的東西

新平台如果還是自建語音，這些會再發生一次：

| 狀況 | 現象 | 對策 |
| --- | --- | --- |
| **來電** | 作業系統把麥克風收走，連線死掉，畫面卻沒反應 | 監聽 track 的 `ended`，把「斷線」和「自己關閉」分開處理，提供重新連線 |
| **背景切換** | iOS 不一定回報背景時死掉的連線 | 回到前景時主動檢查連線狀態 |
| **過隧道** | 短暫 `disconnected` | 給 6 秒緩衝再判定死亡，通常會自己恢復 |
| **模型中途卡住** | 沉默 10 秒，畫面停在「教練說話中」 | 超過 6 秒就說「教練停頓了一下」—— 沉默要有解釋，否則跟死機無法分辨 |
| **斷句太早** | 使用者停下來想，句子被從中間切斷，教練去糾正那個殘句 | 車上要調整 VAD：threshold 0.6、prefix padding 500ms、silence 900ms |
| **辨識語言猜錯** | 帶口音的英文被當成別種語言 | 明確鎖定 `language: "en"` |

**通則：任何「靜默失敗」都是設計缺陷。** 使用者在開車，沒有餘裕去猜發生什麼事。

## 9. 待決問題（新專案要先回答）

### Q1（最重要）逐字稿怎麼從 ChatGPT 出來？

沒有這個，FR-3/4/5/9 全部落空。候選：

- **a.** 抵達後在 ChatGPT 裡下固定指令，請它輸出約定格式，使用者複製貼上到 app。
  可行、零成本、但每次多一個動作。
- **b.** 請 ChatGPT 只輸出**回顧結果**（不含逐字稿），app 只存回顧。省事，但失去
  「重複出現的錯誤」統計的原始依據。
- **c.** 用 ChatGPT 的匯出功能定期匯出，app 批次解析。延遲高，但完全不用手動貼。

**先決定這一題，其他設計才有意義。**

### Q2 開車時到底用什麼？

ChatGPT Voice Mode 的介面不是為開車設計的（沒有大按鈕、沒有狀態指示、會顯示文字）。
需要實際在車上試一次再決定能不能接受。

### Q3 免費 vs Plus

新聞說免費帳號文字無上限。**語音模式是否也無上限、以及 GPT-5.6 Sol 是否只給付費**
需要確認 —— 這決定了成本是 $0 還是 $20/月。

### Q4 作品集價值

ChatGPT-first 的版本，「作品」的部分變成一份提示詞加一個小 app。原本那個
「WebRTC + 額度閘門 + RLS + 狀態機」的完整實作，是更有展示價值的東西。
**如果作品集是目標之一，方案 C（維持現狀）值得重新考慮。**

## 11. 第一週該驗證什麼

不要先寫程式。按這個順序驗證，每一步都可能推翻下一步：

1. **把現有教練指令貼進一個 Custom GPT，在車上用 Voice Mode 開一次 15 分鐘。**
   驗：能不能免手持操作？教練有沒有照指令操練？打斷、停頓的體驗如何？
2. **抵達後在同一個對話裡要求輸出約定格式的回顧。** 驗：格式穩不穩定？能不能解析？
3. **量一次成本**（免費帳號會不會被限流？語音有沒有額度？）
4. **到這裡才決定要不要寫 app**，以及寫哪一半。

## 12. 工作方式（沿用）

這些在上一個專案裡有效，建議延續：

- 先讀規格文件再動手，不要邊做邊猜需求
- 規格有空缺時，做**最保守的 MVP 決策**，但把假設明確寫出來
- 每次交付要說清楚：**改了哪些檔案、驗證了什麼、以及哪些沒辦法驗證**
- 不偷渡沒被要求的功能
- 決策要連同**理由**寫進文件 —— 半年後你只會記得結論，忘記為什麼
